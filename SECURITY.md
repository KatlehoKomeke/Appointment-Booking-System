# Security policy

BranchBook is an engineering assessment for a fictional bank. It holds no real customer data, but it is built as
if it did. This document explains how secrets and personal information are protected, and how to report a problem.

## Reporting a vulnerability

Please report it privately through GitHub: open the repository's **Security** tab and choose
**Report a vulnerability**. Please do not open a public issue for a security problem.

## Secrets

No secret ever enters this repository: not in code, configuration, tests, documentation, screenshots or the git
history.

- **Local development uses throwaway values.** `.env.example` holds placeholders for the local Docker Compose
  database only. `.env` is git-ignored.
- **Hosted environments never see a stored secret.** Database credentials are generated by AWS and injected into
  the running task from AWS Secrets Manager. GitHub Actions reaches AWS through OpenID Connect, so no access key
  exists to leak ([ADR-0006](docs/adr/0006-hosted-demo-on-aws-with-cdk.md)).
- **Every commit is scanned.** `make hooks` enables a pre-commit hook that runs [gitleaks](https://github.com/gitleaks/gitleaks)
  on the staged changes. It also refuses `.env` files, private keys and personal tool settings, even when they are
  force-added.
- **Every push is scanned.** The `secret-scan` workflow scans the full history on every push and pull request, so
  a skipped local hook is still caught.
- **Rules live in [.gitleaks.toml](.gitleaks.toml).** They extend the gitleaks defaults with checks for database
  URLs that contain a password and for AWS account IDs.

### If a secret is committed

1. **Treat it as compromised.** Rotate or revoke it first, before anything else.
2. **Remove it from the history** with `git filter-repo`, then force-push. Every clone must be re-cloned.
3. **Record what happened** and add a scanner rule if gitleaks did not catch it.

Removing a secret from the history does not make it safe again. Rotation is the fix; the cleanup only reduces noise.

## Personal information (POPIA)

BranchBook is designed around the Protection of Personal Information Act, even though all of its data is fictional.

- **Minimal collection (section 10).** A booking stores a first name, a last name and a South African mobile
  number. No ID number, address, date of birth or account number is collected
  ([ADR-0004](docs/adr/0004-restraint-no-login-no-id-number.md)).
- **No exposure.** Full mobile numbers are never displayed. Error bodies never contain personal data or another
  booking's details ([BR-23](docs/domain-rules.md#br-23)).
- **No personal data in logs.** Application logs and PostgreSQL's own error logs carry no names or numbers. A test,
  `LogRedactionTest`, checks this against a real database.
- **Synthetic test data only.** Tests and demos use made-up names and the published demo numbers (`082 555 01xx`).
  Never use a real person's details, including your own.
- **A hosted demo cannot collect real data.** It accepts only the published demo numbers, each locked to a
  fictional persona, and deletes all data after 48 hours.

## Hardening in the application

- **Stateless, with security headers.** No cookies or sessions. A strict `Content-Security-Policy` (`default-src 'self'`)
  is set, and framing is denied.
- **Input is validated at the edge,** and all SQL uses bound parameters.
- **Lookups resist enumeration:** the same 404 for an unknown reference and for wrong digits, and a per-reference
  rate limit.
- **Containers run as a non-root user** with pinned base images; dependencies are pinned and updated through Dependabot.
