# Security policy

BranchBook is an engineering assessment for a fictional bank. It holds no real customer data, but it is built as
if it did. This document explains how secrets and personal information are protected, and how to report a problem.

## Reporting a vulnerability

Please report it privately through GitHub: open the repository's **Security** tab and choose
**Report a vulnerability**, or go straight to
[the private report form](https://github.com/KatlehoKomeke/Appointment-Booking-System/security/advisories/new).
Only you and the repository's administrators can see the report. Please do not open a public issue for a security
problem.

## Secrets

The rule is that no secret enters this repository: not in code, configuration, tests, documentation, screenshots or
the git history. Local development uses throwaway values: [.env.example](.env.example) holds placeholders for the
local Docker Compose database only, and `.env` is git-ignored.

![Where a secret is stopped: before the commit, .gitignore and an opt-in pre-commit hook keep secret files out and run gitleaks, failing closed; push protection blocks provider tokens. Once public, secret-scan reports but blocks nothing, GitHub alerts and CI checks logs. No AWS access key is stored; Secrets Manager is planned after M6.](docs/assets/diagrams/secret-layers.svg)

Layers 1 to 4 act before the code is public. Layers 5 to 7 act after it, so they can report a secret but not keep it
private.

### In place today

1. **.gitignore** ([.gitignore](.gitignore)) keeps `.env` files (`.env` and `.env.*`, but not `.env.example`), keys
   and certificates (`*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.crt`, `*.der`, `id_rsa*`,
   `id_ed25519*`), `credentials` files, `*.secret(s)`, `secrets/`, `.aws/`, `.npmrc`, `.netrc`, `.claude/`,
   `CLAUDE.local.md` and `cdk.context.json` out of `git add`. It can be skipped with `git add -f`; layer 2 then
   refuses the name.
2. **The pre-commit hook refuses blocked file names** ([.githooks/pre-commit](.githooks/pre-commit)): staged `.env`
   files (not `.env.example`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa*`, `id_ed25519*`,
   anything under `.claude/`, `CLAUDE.local.md` and `cdk.context.json`, even when they were force-added. It blocks
   the commit.
3. **The pre-commit hook runs [gitleaks](https://github.com/gitleaks/gitleaks) on the staged diff**: a local
   install if there is one, otherwise v8.30.1 in Docker. It applies gitleaks' default rules plus the two in
   [.gitleaks.toml](.gitleaks.toml): `postgres-url-with-password`, and
   `aws-account-arn`, which catches an account ID inside an ARN, though not a bare 12-digit ID. It fails closed: a
   finding, or having neither gitleaks nor a running Docker, refuses the commit. Both pre-commit checks are opt-in
   (`make hooks`, once per clone), and `git commit --no-verify` skips them.
4. **GitHub push protection** is on for known provider token formats only. Non-provider patterns are off, and GitHub
   does not read `.gitleaks.toml`, so the two custom rules do not apply here. It blocks the push; skipping it takes a
   bypass that GitHub records. From here on, the commits are public.
5. **The secret-scan workflow** ([secret-scan.yml](.github/workflows/secret-scan.yml)) applies the `.gitleaks.toml`
   rules to the full history on every push and pull request, so a skipped local hook is still found after the push.
   It reports but blocks nothing, because `main` has no required checks
   ([docs/delivery.md](docs/delivery.md#known-gaps)).
6. **GitHub secret scanning** finds provider tokens anywhere in the history and raises alerts.
7. **The CI log check** (the `stack` job in [ci.yml](.github/workflows/ci.yml)) fails `ci` if the app or database
   container logs mention `password` or `local-dev-only`, ignoring case.
8. **No AWS access key exists.** GitHub Actions signs in through OpenID Connect, with sessions of at most one hour.
   The role ARN is stored only as the secret `AWS_DEPLOY_ROLE_ARN` of the environment `aws-demo`, and the account ID
   is masked in the workflow logs ([ADR-0007](docs/adr/0007-continuous-deployment-from-main.md),
   [infra/README.md](infra/README.md#how-github-reaches-aws-without-keys)).

The GitHub settings behind layers 4 and 6 can be read with
`gh api repos/KatlehoKomeke/Appointment-Booking-System --jq .security_and_analysis`.

### On the hosted demo

9. **Secrets Manager.** *Built, 2026-10-26.* The database credentials are generated by AWS into the secret
   `branchbook/database` and injected into the Fargate task when it starts, so no database password is ever typed,
   committed or held by GitHub ([ADR-0006](docs/adr/0006-hosted-demo-on-aws-with-cdk.md),
   [infra/README.md](infra/README.md)).

The demo has no sign-in, so it holds no password of its own: a sign-in prompt in front of a demo is a poor
experience for everyone who opens it, reviewers included. The application keeps real personal data out instead:
only the published demo numbers, 082 555 0000 to 082 555 0199, may book (`BRANCHBOOK_BOOKING_DEMO_NUMBERS_ONLY`),
every booking is deleted 48 hours after it is made (`BRANCHBOOK_RETENTION_ENABLED`), and the simulated gateway sends
nothing. Both have been live since 2026-10-26 (058e6fd): a number outside the range gets `422
DEMO_NUMBER_REQUIRED` and nothing is written, and the deletion runs every hour. The simulated inbox is off on the hosted demo
(`BRANCHBOOK_INBOX_ENABLED=false`), so other visitors cannot see anyone's booking; each booker still sees their own
SMS and its status on the confirmation page.

The hosted demo's other controls, all in [infra/lib/app-stack.ts](infra/lib/app-stack.ts) and
[infra/lib/data-stack.ts](infra/lib/data-stack.ts): AWS WAF on the load balancer blocks `/actuator` (403), allows 30
booking `POST`s per address in five minutes and applies AWS's managed rules for known bad inputs and addresses;
HTTPS uses ELB's recommended TLS 1.3 policy, plain HTTP is redirected to HTTPS, and HSTS keeps browsers there; the task
accepts only the load balancer, and the database, in subnets with no route to the internet, accepts only the task,
over TLS (`rds.force_ssl`), encrypted at rest. PostgreSQL's own log is not exported, because a constraint error's
detail line can quote a mobile number, and the application's logs are kept for seven days.

### If a secret is committed

1. **Treat it as compromised.** Rotate or revoke it first, before anything else.
2. **Remove it from the history** with `git filter-repo`, then force-push. The `Protect main` ruleset refuses
   force-pushes, so switch it off for that one push (Settings, Rules) and on again straight after. Every clone must
   be re-cloned.
3. **Record what happened** and add a scanner rule if gitleaks did not catch it.

Removing a secret from the history does not make it safe again. Rotation is the fix; the cleanup only reduces noise.

## Personal information (POPIA)

BranchBook is designed around the Protection of Personal Information Act, even though all of its data is fictional.

- **Minimal collection (section 10).** *Built.* A booking stores a first name, a last name and a South African mobile
  number. No ID number, address, date of birth or account number is collected
  ([ADR-0004](docs/adr/0004-restraint-no-login-no-id-number.md)).
- **No exposure.** *Built in M3.* Once an appointment exists, the API never returns its full mobile number: the
  caller who booked it, or who has just proved its last four digits, sees `082 *** 0101`. The simulated inbox,
  built in M4, shows only `082 *** ****`, and is off unless a deployment switches it on (`branchbook.inbox.enabled`);
  its retry, built in M6, exists only with it and can do no more than make a failed message due again
  ([BR-19](docs/domain-rules.md#br-19); `AppointmentApiIT.responsesNeverContainUnmaskedMobile`,
  `InboxApiIT.listsTheNewestMessagesWithTheirReferencesAndRedactedRecipients`).
  Error bodies never contain personal data or another booking's details ([BR-23](docs/domain-rules.md#br-23)).
- **No personal data in logs.** *Built: the database and driver settings in M1, the log proof in M3.* Application
  logs and PostgreSQL's own error logs carry no names or numbers:
  - PostgreSQL logs errors tersely, without the DETAIL line that quotes a constraint's conflicting values (set in
    `compose.yaml` and for the test database).
  - The JDBC driver leaves those values out of its exception messages;
    `SchemaConstraintIT.violationMessagesNeverQuoteTheConflictingValues` checks this.
  - Unexpected exceptions are logged with their types and stack frames but never their messages;
    `ProblemDetailHandlerTest` and `ErrorDispatchControllerTest` check this.
  - Hibernate's own SQL error log, which repeats the database's message, is switched off; the booking module logs
    only the constraint name and SQLSTATE.
  - `LogRedactionIT.bookingLogsContainNoCustomerNameOrMobile` takes one synthetic customer through every outcome
    of a booking and a lookup, then checks the application's log and PostgreSQL's for their name, their number in
    any form, masked or not, and the appointment's reference.
    `LogRedactionIT.cancelAndRetryLogsContainNoCustomerNameMobileOrReference` does the same for a cancellation and
    the retry of its messages.
- **Log lines name appointments by id.** *Built in M3.* A reference and the last four digits open an appointment, so log
  lines carry the appointment's id and never its reference.
- **Synthetic test data only.** Tests and demos use made-up names and the published demo numbers: `082 555 01xx`,
  and `082 555 0000`, which the simulated gateway always refuses, to show a failed delivery. The demo data that
  docker compose books on a fresh database uses `+27 60 000 0001`, `+27 60 000 0002` and `+27 60 000 0000`, the last
  refused like any number ending 0000, with the fictional surname Demo ([api/README.md](api/README.md#demo-data)).
  Never use a real person's details, including your own.
- **A hosted demo cannot collect a real number.** *Built; on in the hosted demo only.* While
  `branchbook.booking.demo-numbers-only` is true (`BRANCHBOOK_BOOKING_DEMO_NUMBERS_ONLY=true`), a booking is taken
  only for the demo block, `082 555 0000` to `082 555 0199`. Any other South African mobile is refused with
  `422 DEMO_NUMBER_REQUIRED` before anything is written, so a real person's number is never stored or sent an SMS,
  and the refusal never repeats the number (`DemoNumbersOnlyIT.aNumberOutsideTheBlockIsRefusedOnItsFieldAndWritesNothing`,
  `MobileNumberTest.theDemoBlockRunsFrom0825550000To0825550199`). The start-up log says which numbers bookings take.
  Nothing real is ever sent: the SMS gateway is simulated. On the hosted demo the simulated inbox is off, so no
  visitor can list other people's bookings, and every booking is deleted with the purge below. Names are free text;
  the form and the privacy page ask for a made-up one. ADR-0006 planned to lock each demo number to a fictional
  persona; the block and the purge were built instead
  ([ADR-0006](docs/adr/0006-hosted-demo-on-aws-with-cdk.md)).
- **The hosted demo deletes every booking after 48 hours.** *Built; on in the hosted demo only.* While
  `branchbook.retention.enabled` is true (`BRANCHBOOK_RETENTION_ENABLED=true`), a job runs every hour, from a minute
  after start-up, and deletes every appointment booked `branchbook.retention.max-age` ago or earlier (`PT48H`, set by
  `BRANCHBOOK_RETENTION_MAX_AGE`). It deletes all appointments of that age, whatever their status, and with each one
  its SMS messages, which hold the number and the reference, and its idempotency keys. So within about an hour of a
  booking turning 48 hours old, nothing the customer typed is left in the live database. Backups are not purged: the
  hosted demo's automated database backups can restore a deleted booking until they expire, seven days after they
  were taken, and tearing the database down keeps a final snapshot until someone deletes it
  ([ADR-0006](docs/adr/0006-hosted-demo-on-aws-with-cdk.md)). The branches, services, hours and holidays are never
  touched. Only the hosted demo's ECS task definition switches it on. It is off by default, so `make up`,
  `make dev-api` and the tests keep their bookings until you delete them, as the privacy page says of a local copy. A
  max-age under 24 hours, the life of an `Idempotency-Key`, stops start-up, so a retry can never book a purged
  appointment again. Each run logs one line of counts (`retention.purged appointments= messages= keys=`) and nothing
  else (`RetentionPurgeIT`, `RetentionPurgeJobTest`).

## Hardening in the application

- **Stateless, with security headers.** No cookies or sessions. A strict `Content-Security-Policy` (`default-src 'self'`)
  is set, and framing is denied
  ([SecurityConfig.java](api/src/main/java/za/co/fynbos/branchbook/shared/security/SecurityConfig.java)).
- **Input is validated at the edge,** and all SQL uses bound parameters.
- **Lookups resist enumeration.** *Built in M3.* The same 404 for an unknown reference and for wrong digits, and a
  per-reference rate limit: five wrong lookups block a reference for an hour from the first
  ([BR-13](docs/domain-rules.md#br-13)).
- **Containers run as a non-root user** with pinned base images ([Dockerfile](Dockerfile)).
- **Dependencies are pinned and updated through Dependabot** ([dependabot.yml](.github/dependabot.yml)). Dependabot
  alerts and security updates are on. Code scanning is not configured.

## Pipeline access

The pipeline reaches AWS with no stored key, and its role can only assume the CDK bootstrap roles and read one
parameter. That it never changes its own access is enforced by the CDK app and the deploy workflow, not by IAM. What
IAM, GitHub and the code each enforce, and what is not prevented today, are in
[infra/README.md](infra/README.md#who-can-change-what-in-aws).

## Known risks

These risks are accepted in v1, or reduced but not closed. Each has the control production would add.

| Risk | Today | Production control |
|---|---|---|
| **Unauthenticated SMS sending.** Anyone can book with any South African mobile number, which invites SMS pumping, harassment and slot squatting. | Open by design ([ADR-0004](docs/adr/0004-restraint-no-login-no-id-number.md)). v1 sends nothing real: confirmations go to a simulated gateway (built in M5), and the hosted demo accepts only the published demo numbers. | An OTP before an appointment counts as confirmed, per-recipient and per-prefix caps, CAPTCHA, blocking premium-rate prefixes, and cost alerts |
| **Learning that a number has a booking.** Booking with another person's number returns `409 DUPLICATE_APPOINTMENT` or `409 CUSTOMER_OVERLAP`, though never the reference, branch or time ([BR-23](docs/domain-rules.md#br-23)). | Accepted for the demo | OTP verification of the number before any answer |
| **Reference enumeration.** Guessing references to find appointments. | Built in M3: eight characters from a 31-symbol alphabet, the same 404 for an unknown reference and for wrong digits, and the lookup rate limit ([BR-13](docs/domain-rules.md#br-13)) | Appointments bound to a verified customer through the bank's identity provider |
| **Blocking someone's lookup.** Five wrong tries, lookups and cancels together, block a known reference for an hour, and the counts are kept in memory for one instance ([docs/architecture.md](docs/architecture.md#lookup)). | Accepted: a reference appears only in the customer's own SMS and pages | A shared rate-limit store, and identity-bound lookups |
| **Cancelling with a leaked reference.** The reference and the last four digits that open an appointment also cancel it. | Accepted for the demo: the same credential and rate limit as a lookup ([BR-13](docs/domain-rules.md#br-13)), no cancel once the appointment has started, and a cancellation SMS to the booked number ([BR-14](docs/domain-rules.md#br-14)) | An OTP to the booked number before a cancel, and identity-bound appointments |
| **The pipeline's access boundary.** IAM alone does not stop a change pushed to `main` from deploying with wider access. | One administrator collaborator and the `aws-demo` branch policy | The hardening options in [infra/README.md](infra/README.md#who-can-change-what-in-aws) |
| **The hosted demo's database certificate is not verified.** `sslmode=require` encrypts the connection to RDS but does not check the server's certificate, so it does not stop an impostor inside the VPC. | Accepted for the demo: the database is reachable only from the task's security group, in subnets with no internet route | `sslmode=verify-full` with the RDS certificate bundle in the image |
| **Opening another visitor's booking on the hosted demo.** The demo has no sign-in, and a demo number's last four digits are public, so anyone who learnt a booking's reference could open it and see the name typed into it, or cancel it. The simulated inbox would list every reference. | Reduced: the inbox is off on the hosted demo (`BRANCHBOOK_INBOX_ENABLED=false`), so `/api/v1/messages` answers 404 and a reference appears only on its booker's confirmation page; guessing one meets the lookup rate limit ([BR-13](docs/domain-rules.md#br-13)) | The inbox stays off (`branchbook.inbox.enabled` defaults to false), and lookups are bound to a verified customer |
